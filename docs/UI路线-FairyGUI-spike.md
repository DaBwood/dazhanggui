# UI 路线 spike：FairyGUI in Godot（2 天）

> 目的：回答一个问题——**要不要为了 FairyGUI 换引擎？**
> 结论先行：**不换引擎，先花 2 天把 FairyGUI 接进 Godot 试一页。** 通过就换 UI 层，不通过就回 B3 的 Godot 页面壳。
> 背景：Godot 4.7 已有一个纯 GDScript 的 FairyGUI 运行时（[citizenll/FairyGUI-godot](https://github.com/citizenll/FairyGUI-godot)，MIT，0.4.0，2026-07 上架 Asset Library）。

---

## 1. 为什么是 spike，不是直接决定

- 换 Cocos 的代价是**重写 42k 行逻辑**，不是换 UI；而现在的痛点是架构（14 项链、7 套收益罐），换引擎不解决。
- FairyGUI 的价值在**复杂 UI 的编辑效率**，不在逻辑；把它接进 Godot，可以只换 UI 层。
- 但这个 Godot 运行时是 0.4.0、社区项目，必须用一页真实界面验证，不能只看 README。

---

## 2. 时间盒

**2 天**。第 1 天接运行时 + 做一页；第 2 天压测 + 写结论。超时即判负，回 B3。

---

## 3. 步骤

### Day 1

1. 开分支 `spike/fairygui`（从 `d584beb`）。
2. 把 [FairyGUI-godot](https://github.com/citizenll/FairyGUI-godot) 的 `addons/fairygui` 拷进项目，启用插件。
3. 用 FairyGUI Editor 做一页：**酒肆主页**（对应现有 `tavern_view.gd`）：
   - 顶栏：返回 + 标题 + 勋章按钮；
   - 三张作坊卡（列表）；
   - 一个设施详情弹窗；
   - 一个 100 项的虚拟列表（压测用）。
   - 素材先用现有 PNG/纯色占位，不追求好看。
4. 导出 `.fui`，放进 `res://ui_spike/`，在 Godot 里用 `FGUIView` 加载。
5. 接 10 个按钮事件（返回/勋章/3 张卡/弹窗关闭/确认等），用生成的 `UI_*` 强类型脚本。

### Day 2

6. 压测：600×1067 下滚动 100 项列表、连点按钮、开/关弹窗，记录 FPS 与卡顿。
7. 记录数据（见 §4）。
8. 写结论：`docs/UI路线-结论.md`，给出「采用 / 不采用」与理由。

## 5. 判定规则

**采用 FairyGUI**（全部满足）：

- 页面行数 ≤ 现有 1/3；
- 100 项列表 60fps；
- 10 个事件全通；
- 0 阻断报错；
- 接线不需要改 `game_controller` / `game_data` 的核心。

**不采用**（任一满足）：

- 运行时崩溃/白屏/输入错乱，2 天内修不好；
- 列表掉帧到 30fps 以下；
- 需要改引擎源码或大量 C#；
- 接线成本高于 B3 的页面壳。

---

## 6. 如果采用：后续怎么落

1. 新增 `ui/fgui/` 目录：`.fui` 包 + 生成的 `UI_*` 脚本 + 一个 `FGUIPageAdapter`（把 `c`/`data` 注入，替代 `BaseView` 的壳）。
2. 先迁 3 页：`tavern_view`、`bank_view`、`winery_view`；逻辑不动，只换 UI。
3. 新页面一律 FairyGUI；旧页面按「闹心程度」迁，不追全量。
4. B3 的 `MedalTrack` 照做；页面壳部分取消。
5. 保留 `BaseView` 给不迁的页，两个栈并存，不搞大爆炸。

---

## 7. 重要前提：原作的 UI 包不一定能直接用

- 原作的 FairyGUI 包是 Cocos 2.4 构建的 `.bin` + 图集；Godot 运行时吃的是 `.fui`。格式同源但版本/扩展名可能不同，**先拿一个包试**，不要假设能直接加载。
- 即使能加载，图集纹理是 `lyqszp` 加密的（见 [资源提取-路线](资源提取-路线.md) §3），**纹理没解开，原 UI 也看不见**。
- 所以这次 spike 的目标是「FairyGUI 的**编辑效率**」，不是「直接复用原 UI」。后者要等纹理解密。

---

## 8. 不做什么

- 不迁 40 页，只做 1 页。
- 不动 `systems/`、不改存档、不改数值。
- 不引入 C#/GDExtension。
- 不因为 spike 好看就立刻全量替换；先并存。
