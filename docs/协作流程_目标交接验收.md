# 四段式协作流程：目标 → 交接 → 实现 → 验收

> 适用：边界清楚、可机械执行的批量改造（换肤、迁移、统一组件、批量修文案）。
> 不适用：需求还在探索、需要视觉试错、跨模块重构——那些直接做原型更快。

## 角色

| 角色 | 负责 |
|---|---|
| 用户 | 提目标、拍板、真机验收、push |
| 主 AI（DSH） | 澄清目标、写目标单/交接单、复核代码、出验收单 |
| 执行 AI（Kimi） | 按交接单实现、填实现报告、按验收单返修 |

核心原则：**交接单是合同，实现报告是交付凭证，验收单是签收单。** 三样都不省。

## 四件套

### 1. 目标单（主 AI 写，用户确认）

```markdown
# 目标：<一句话>
## 背景
<为什么要做，现状是什么>
## 范围
- 做：<文件/页面/函数清单>
- 不做：<明确排除项>
## 验收标准（DoD）
1. <可观察结果，例：某弹窗打开后是纸底卡片，无暗紫底>
2. <可观察结果，例：数值/按钮行为与改前一致>
3. <可观察结果，例：解析通过，无 SCRIPT ERROR>
## 风险 / 依赖
<需要用户先做的事：push、给素材、确认口径>
```

### 2. 交接单（主 AI 写）

```markdown
# 交接：<任务名>
## 先决条件
<基线 commit / 需先 push / 需先导入素材>
## 可用 API / 参考资料
<签名、返回值、样例代码>
## 逐项任务
1. <文件>：<函数>：<怎么改>（附 before/after 片段）
## 禁止事项
<不碰的范围、不顺手优化、不改数值>
## 自检
<命令 / 静态检查项>
## 交付格式
<diff 摘要 + 影响清单 + 实现报告>
```

### 3. 实现报告（执行 AI 填，随交付一起回）

```markdown
# 实现报告：<任务名>
## 改动
- <文件>：<函数>：<一句话>
## 自检
- 解析/加载：<结果>
- 符号核实：<引用的函数/字段是否 grep 过>
- 范围核对：diff 是否只含目标块
## 偏离交接单的地方
<没有就写“无”；有就写原因>
## 遗留 / 疑问
<需要用户或主 AI 拍板的点>
```

### 4. 验收单（主 AI 写）

```markdown
# 验收：<任务名>
结论：PASS / FAIL
## 问题
- P0 阻断：<必须修，否则不能用>
- P1 应修：<影响体验/一致性>
- P2 可选：<优化建议，不阻断>
## 复核依据
<diff 范围、符号、结构、逻辑一致性>
```

## 流程

1. 用户发目标（一句话 + 范围 + 期望效果）。
2. 主 AI 只问**影响实现**的问题（3–5 个），不铺垫。
3. 用户确认 → 主 AI 出目标单 + 交接单，符号先 grep 核实。
4. 执行 AI 按单实现，**一次一批**（建议 ≤1 个页面或 ≤5 个文件），回实现报告。
5. 主 AI 复核 diff + 报告，出验收单（PASS 或编号问题）。
6. PASS → 用户真机验交互 → push；FAIL → 问题清单回执行 AI 修一轮。

## 硬规则

- 一次一批，diff 只含目标范围；跨页大改不接受。
- 交接单里引用的每个符号，主 AI 必须先 grep 确认存在。
- 执行 AI 不许“顺手优化”、不许改范围外、不许重排整文件。
- 有歧义先问，不猜；猜错的返修成本比问一句高。
- 验收标准必须可观察（能点、数值对、无报错），不写“看起来更好”。
- 实现报告不填 = 交付不完整。

## 成本控制

- 复核只看 diff + 实现报告，不重读全文件。
- 问题攒成一批回给执行 AI，不要一条一修。
- 文档进仓库、随代码版本化，下一次直接引用，不重新口述。
- 视觉微调优先在 Godot 编辑器里做，不占对话轮次。

## 什么时候跳过这套

- 改一两行、边界明确：直接说，不用文档。
- 需求还没定：先做预览/原型，定稿后再进流程。
- 需要我直接写代码才稳的（跨文件重构、存档迁移、公式改动）：不走外包。
