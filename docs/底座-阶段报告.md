### 与交接文档的 3 处偏差（都是有意的）

1. **`get_shop_modifier_sum` 改名 `get_shop_multiplier`，且从 1.0 起累加。**
   交接文档给的写法是 `total := 0.0` 求和、外面再 `1.0 + sum`。浮点加法不满足结合律，
   `1.0 + (0.0 + A + B + …)` 与 `((1.0 + A) + B) + …` 的尾数可能不同，`int()` 截断处就有可能出现 1 的差。
   现在按「从 1.0 起、按原顺序逐项加」实现，与原链的运算次序**逐位一致**，不是「误差够小」。

2. **F2 档位从「50 关」改成「650 关」。**
   交接文档写「`stage_main = 50`，解锁前 10 家店」，但 50 关只开 4 家（客栈 1 / 医馆 5 / 说书摊 15 / 香料铺 40）。
   第 10 家（酒坊）在 650 关。按文档原样跑，F2 只能覆盖 4 家店，达不到「中期」意图。

3. **没有开分支、没有每阶段 commit。**
   用户口径：AI 不 commit。改动留在 `main` 工作区，验收后由用户提交。

### 踩到的坑（写给下一个改测试的人）

- `extends SceneTree` 的脚本里，**在 `_initialize()` 里直接 `quit()` 会在引擎退出清理阶段段错误**（退出码 `0xC0000005`）。
  现在改成 `_initialize()` 只算结果，`_process()` 第一帧再 `quit()`，退出码稳定 0。
- 试图用「遍历 `_system_instances`，把每个系统的 `g` 置 null」打断 RefCounted 循环，会**直接段错误**。
  现在的做法是不打断，接受退出时 `ObjectDB instances were leaked` / `resources still in use` 的已知噪声（与工程基线一致）。
- 门客收入有静态缓存（`HeroData._income_cache`）。fixture 改完状态必须 `HeroData.invalidate_income_cache()`，否则读到上一个 fixture 的数。

## B2 · 时间结算双原语（2026-10-28 完成）

### 预检结论：交接稿的客栈/酒肆映射不成立

交接稿 §5 原定「只迁 `inn_system.gd` / `tavern_system.gd`」，映射表写 `pending/pending_ts`、`jar/jar_ts`。
对着现码逐行核，**这两个字段不存在**，两个系统也都不是「速率 × 时长」的收益罐：

| 系统 | 真实结算形态 | 关键证据 | 是速率罐？ |
|---|---|---|---|
| 客栈 | **有限批次作业**：一次下 `count` 份，每份 `seconds` 秒，`done = min(count, floor(dt/secs))`，产出进 `pending` 袋后等玩家再下单 | `inn_system.gd:27` `:107` `:112-132` | 否 |
| 酒肆 | **离散恢复计时器**（叫号：`interval/cap/ts`，余数保留）+ **事件驱动罐**（每接待一位客人 `jar_yintiao += income`） | `tavern_system.gd:33` `:150-155` `:214` `:235-237` | 否 |
| 妙音坊 | **真·浮点三轨罐**：`jar = {last, yyb, yyw, yyf}`，`settle_jar()` 按 `elapsed_min × rate` 累加，`claim` 取整扣减、保留小数 | `miaoyin_system.gd:87` `:144` `:591-604` | **是** |
| 钱庄 | **tick 量化罐**：`clamp(dt, 0, cap_seconds)` → `ticks = floor(secs/tick_seconds)`，领取后重置 `start_time` | `bank_system.gd:126-140` `:148`；`data/bank.json` `tick_seconds=1200` `cap_seconds=86400` | 是（量化变体） |
| 庄园 | **浮点产量罐**：`elapsed/60 × rate` 入库；在线无上限，离线按 24h 封顶 | `manor_system.gd:231-240` `:245-260` | **是** |
| 医馆 | **离散恢复计时器**（病人）+ 事件驱动罐（每次结算 `jar_yishu += preview`） | `clinic_system.gd:122-127` `:260` | 否（罐部分） |
| 药铺 | **离散恢复计时器**（体力）+ 后台队列逐条处理（`budget_ms`） | `drugshop_system.gd:120-124` `:180+` | 否 |

行号以 2026-10-28 工作区为准，会漂移；按符号 grep。

按交接稿「字段名对不上就停下来写报告，不要猜」的规矩，这里没有硬套。
实际存在三类原语，不是一类：

1. **Accrual（连续时间窗）**：浮点 `单位数 × 产出率`，可封顶。→ 妙音坊、庄园。
2. **RegenTimer（离散恢复）**：整数单位，`gained = floor(dt/interval)`，`ts += gained × interval` 保留余数。→ 酒肆叫号、医馆病人、药铺体力。
3. **BatchJob（有限批次）**：`count × duration`，到点产出。→ 客栈烹饪、促织培育。

2026-10-28 拍板走「双原语」口径：Accrual + RegenTimer；客栈/钱庄/促织**明确不迁**。

### 与交接稿的偏差（都是有意的）

1. **`Accrual` 不是交接稿里的 `rates/stored/peek/claim/to_dict/from_dict` 状态罐，而是纯时间窗函数。**
   妙音坊的应援物不是单一速率：按居住建筑逐栋、按职业概率卷积；庄园是按品种把产量映射到产物名。
   把这些压成 `rate(key) × seconds` 会改变浮点运算次序（分配律不保尾数），无法做到逐字节一致。
   现在 `Accrual` 只接管「elapsed + cap + 回拨」这段重复逻辑，产出公式原样留在各系统里。
2. **`RegenTimer` 不持有状态。**
   酒肆/医馆/药铺的 `jiaohao`、`patients`、`stamina`、`*_time` 是存档字段，不能换形状。
   所以 `apply()` 返回 `[new_value, new_ts]`，调用方写回原字段；存档键与结构零变化。
3. **新增 `Clock` 测试钩子。**
   交接稿要求 Accrual 不读系统时间；`Clock` 是系统侧的取时口，运行时 `override_now = -1`，行为与原来完全一致。
   没有它，`claim_jar()` 等内部再次结算的路径无法用假时钟驱动。
4. **迁移 5 个系统，不是交接稿的 2 个。**
   客栈是批次作业、酒肆是恢复计时器+事件罐，硬迁会改玩法语义；改为迁真正同形的 5 个。
5. **多一个原语测试脚本。**
   系统级快照保证「和改前一样」，原语测试保证「新代码自身边界对」；两份职责分开。

### 没迁的，及理由

| 系统 | 形态 | 为什么不迁 |
|---|---|---|
| 客栈 | BatchJob | 有限批次 `count × duration`，不是连续速率；迁进 Accrual 会变成「一直产出」 |
| 钱庄 | tick 量化 + 领取重置 | `ticks = floor(secs/tick_seconds)` 是先量化再乘；Accrual 的连续累加会在 `floor()` 处产生 1 的差，达不到逐字节一致 |
| 促织 | 单件倒计时 | 同 BatchJob；`start_peiyu`/`speedup` 改的是 `start_time`，没有累计量 |
| 酒肆银条 | 事件驱动 | 每接待一位客人 `jar_yintiao += income`，与时间无关 |
| 医馆医术 / 药铺队列 | 事件驱动 | 每次结算/每条病人入罐，与时间无关 |

### 踩到的坑（写给下一个改测试的人）

- **快照里的 Dictionary 必须 `duplicate(true)`。** 直接塞 `g.manor_goods` / `m.jar["yyw"]` 会拿到同一个引用；后续 `_add_production` / `_produce_minutes` 原地改它，JSON 落盘时所有步骤都变成最终状态。第一版 baseline 就踩了这个，`manor.init` 里出现了 40740。
- **浮点快照必须 `JSON.stringify(root, "", true, true)`。** 第 4 个参数 `full_precision=false` 时，`1.2345678901234567` 会被截成 `1.23456789012346`，重构前后可能“看起来一样”但尾数已丢。
- **`Clock.override_now` 要在 `GameData.new()` 之前设。** 否则 `_new_jar()` / `load_save_data()` 里的初始化时间戳会落成真实时间。
- `extends SceneTree` 的脚本仍在 `_process()` 第一帧 `quit()`；`_initialize()` 里直接退会段错误（B1 的坑，B2 复用）。
